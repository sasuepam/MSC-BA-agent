CR: PayPal Reconciliation – Acquirer Auth Code in Apply Payment

Interface: INT007, INT146 | Initiative: DTTP – PayPal Reconciliation | Status: Draft

Summary

When a customer pays by PayPal on the new MSC website, the OPT booking reference is not available at the time of payment capture, leaving the Finance team unable to reconcile PayPal transactions to bookings without manual intervention. The agreed short-term solution (ADR0023 Option B) is to pass the acquirerAuthorizationCode — a unique reference shared between DataTrans and PayPal at the time of authorisation — through to SAP via the existing optional field DtsApplyPaymentRequestMessage.Payment.ReferenceNo in the Apply Payment API. This change affects two existing interfaces: INT007 (DTS Apply Payment – booking funnel) and INT146 (DTS Apply Payment – MyMSC private area).

Change Scope

  • INT007 and INT146 must source acquirerAuthorizationCode from the DataTrans status response (detail.authorize.acquirerAuthorizationCode) when the transaction is in "authorized" state (e.g. Klarna), where the value is already present in the status response.
  • INT007 and INT146 must source acquirerAuthorizationCode from the DataTrans authorize-split response (detail.authorize.acquirerAuthorizationCode) when the transaction is in "authenticated" state (e.g. PayPal, Card, Apple Pay, Google Pay), where the value is absent from the status response.
  • When an acquirerAuthorizationCode is available, both interfaces must map it to DtsApplyPaymentRequestMessage.Payment.ReferenceNo before calling the DTS Apply Payment API.
  • When no acquirerAuthorizationCode is available for a given payment method (e.g. Card, Apple Pay, Google Pay), ReferenceNo must be left absent or null and the Apply Payment call must proceed without error.
  • The acquirerAuthorizationCode value must be passed through to SAP without any transformation, truncation, or encoding.
  • No new API fields are introduced and no changes are required to the DTS Apply Payment API contract or to existing API consumers.

Interfaces Affected

  • INT007 — DTS Apply Payment – booking funnel (MuleSoft, DataTrans, DTS, SAP)
    INT007 must be updated to extract detail.authorize.acquirerAuthorizationCode from the DataTrans status response (transaction in "authorized" state) or from the DataTrans authorize-split response (transaction in "authenticated" state), and populate DtsApplyPaymentRequestMessage.Payment.ReferenceNo with this value before calling the DTS Apply Payment API. If no acquirerAuthorizationCode is available, ReferenceNo is left absent or null and no error is raised.
  • INT146 — DTS Apply Payment – MyMSC private area (MuleSoft, DataTrans, DTS, SAP)
    INT146 must apply the same sourcing and mapping logic as INT007: extract detail.authorize.acquirerAuthorizationCode from the appropriate DataTrans response based on transaction state and populate DtsApplyPaymentRequestMessage.Payment.ReferenceNo accordingly. If no acquirerAuthorizationCode is available, ReferenceNo is left absent or null and no error is raised.

Rationale

  • On the old MSC website the OPT booking was created before payment, so the booking reference was available in PayPal at capture time; on the new website the booking is created after payment, meaning no booking reference is present at the point of PayPal capture.
  • This leaves the Finance team unable to automatically reconcile PayPal transactions to bookings, creating a manual overhead and a risk of unmatched payments.
  • The acquirerAuthorizationCode is generated by DataTrans during the authorisation step, is shared with PayPal, and provides SAP with a reliable reconciliation key that matches a value visible in both the DataTrans portal and PayPal.
  • ADR0023 evaluated multiple options; the preferred long-term solution (DataTrans PATCH API to write the booking reference back to PayPal post-capture) is not achievable in the near term as it is not on the DataTrans roadmap.
  • Reusing the existing optional field ReferenceNo in the Apply Payment request requires no DTS API development, has no impact on existing API consumers, and is the lowest-risk near-term option (ADR0023 Option B).

Acceptance Criteria

GIVEN a PayPal payment has been completed in the booking funnel and the DataTrans transaction is in "authenticated" state when INT007 calls the status endpoint
WHEN INT007 calls the DataTrans authorize-split endpoint (POST /v1/transactions/{transactionId}/authorize) and receives a response containing detail.authorize.acquirerAuthorizationCode
THEN INT007 maps the acquirerAuthorizationCode value to DtsApplyPaymentRequestMessage.Payment.ReferenceNo and calls the DTS Apply Payment API with the field populated; SAP receives the Apply Payment request with the correct ReferenceNo value; the value matches the "Acquirer authoriz code" visible in the DataTrans portal for the same transaction

GIVEN INT007 has successfully retrieved the acquirerAuthorizationCode from the DataTrans authorisation response
WHEN INT007 calls the DTS Apply Payment API
THEN INT007 uses the correct HTTP method, endpoint URL, authentication headers, and payload schema as defined in the Apply Payment API contract (Apply payment R140 from DTS); the request body conforms to the DtsApplyPaymentRequestMessage schema with Payment.ReferenceNo populated; the DTS Apply Payment API returns the agreed success response code

GIVEN a PayPal payment has been completed in the MyMSC private area and the DataTrans transaction is in "authenticated" state
WHEN INT146 calls the DataTrans authorize-split endpoint and receives a response containing detail.authorize.acquirerAuthorizationCode
THEN INT146 maps the value to DtsApplyPaymentRequestMessage.Payment.ReferenceNo and calls the DTS Apply Payment API; SAP receives the Apply Payment request with the correct ReferenceNo value; the value matches the DataTrans portal entry for the same transaction

GIVEN INT146 has successfully retrieved the acquirerAuthorizationCode from the DataTrans authorisation response
WHEN INT146 calls the DTS Apply Payment API
THEN INT146 uses the correct HTTP method, endpoint URL, authentication, and payload schema consistent with the Apply Payment API contract; the request body conforms to the DtsApplyPaymentRequestMessage schema with Payment.ReferenceNo populated; the DTS Apply Payment API returns the agreed success response code

GIVEN a Klarna payment has been completed and the DataTrans transaction is in "authorized" state when INT007 or INT146 calls the status endpoint
WHEN the integration reads detail.authorize.acquirerAuthorizationCode from the DataTrans status response (GET /v1/transactions/{transactionId})
THEN the integration maps the value to DtsApplyPaymentRequestMessage.Payment.ReferenceNo and calls the DTS Apply Payment API without making an additional authorize-split call solely to obtain the auth code; SAP receives the Apply Payment request with the correct ReferenceNo value

GIVEN a Klarna payment where the DataTrans status response already contains the acquirerAuthorizationCode
WHEN the integration processes the payment
THEN the integration does not make an additional authorize-split call solely to obtain the acquirerAuthorizationCode; the value in Payment.ReferenceNo matches the value from the status response; the integration flow log confirms the call sequence is status then Apply Payment with no redundant authorize-split call

GIVEN a Card payment processed via INT007 or INT146 where neither the DataTrans status response nor the DataTrans authorisation response contains an acquirerAuthorizationCode
WHEN the integration calls the DTS Apply Payment API
THEN the Apply Payment request is sent with Payment.ReferenceNo absent or null (consistent with the field being optional); the DTS Apply Payment API accepts the request and returns the agreed success code; no error is logged for the absence of ReferenceNo

GIVEN an Apple Pay or Google Pay payment processed via INT007 or INT146 where no acquirerAuthorizationCode is available from either the DataTrans status response or the authorisation response
WHEN the integration calls the DTS Apply Payment API
THEN the Apply Payment request is sent without ReferenceNo; the DTS Apply Payment API returns the agreed success code; the integration completes successfully; no error is logged relating to the missing acquirerAuthorizationCode for these payment methods
