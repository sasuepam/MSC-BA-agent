BA Stories – INT142 Prepaid Bookings: Excursions and Onboard Services Fields Added

Splitting Rationale

This specification covers a single existing interface: INT142 (MyMSC Booking Details). All changes described — adding longDescription for both excursions and onboard services, adding duration and MinPaxRequired for excursions, and adding the full ActivityMoreInfo flag set for excursions — are field mapping enrichments to the same INT142 API response. They share a single upstream source (the excursions API or onboard services API), a single target response contract, and a single delivery context. Per the splitting rules, same-feature changes to a single existing interface are grouped into one CR.

The fallback/resilience behaviour for retired excursions (TC-003 in the spec) is noted as [TO BE CONFIRMED] pending UX and product alignment, and the expected fallback data strategy is not yet defined. This scenario is out of MuleSoft scope for this CR and has not been included in acceptance criteria.

ADF interfaces excluded: None referenced in this specification.

Change Requests

CR-001

Type: CR

Summary: INT142 Add Prepaid Item Fields for Excursions and Onboard Services

Description

Change Scope:

INT142 (MyMSC Booking Details) API response is to be enriched with the following new fields for prepaid items. All mappings are from upstream provider APIs to the INT142 response payload.

Rationale:

Customers in the MyMSC private area who have prepaid excursions or onboard services can currently see only limited information about those items. Adding longDescription across all prepaid items, and adding duration, MinPaxRequired, and the full ActivityMoreInfo flag set for excursions, provides customers with the detail they need to review their purchases, plan their time at each port of call, and understand group size constraints and activity characteristics before departure.

Acceptance Criteria (BDD)

TC-001 – Happy Path: Booking with prepaid excursion and prepaid onboard service

Given an authenticated customer has a booking containing at least one prepaid excursion
  and at least one prepaid onboard service
  and the upstream excursions API returns values for all new source fields
  including a non-empty guideLanguageCodes array
When the customer calls GET INT142 for that booking
Then an HTTP 200 is returned
And the prepaid excursion item in the response contains longDescription as a string
And the prepaid excursion item contains duration with the agreed type and format
And the prepaid excursion item contains MinPaxRequired with the agreed type
And the prepaid excursion item contains an ActivityMoreInfo object
And all ActivityMoreInfo flag fields (BestSeller, Bus, ByFoot, Cultural, Drink, ForFamily,
  Lunch, NoFilm, NoGuide, Shopping, Snack, Swim, Tasting, Tour, WalkingDifficulty,
  Wheelchair, NbrMaxWaitList, BestRated) are present and of boolean type
And ActivityMoreInfo.GuideLang is an array of strings
And the prepaid onboard service item contains longDescription as a string
And the prepaid onboard service item does not contain duration, MinPaxRequired,
  or ActivityMoreInfo

TC-002 – Happy Path: Booking with prepaid onboard service only (no excursions)

Given an authenticated customer has a booking containing at least one prepaid onboard service
  and no prepaid excursions
When the customer calls GET INT142 for that booking
Then an HTTP 200 is returned
And the prepaid onboard service item contains longDescription as a string
And the prepaid onboard service item does not contain duration, MinPaxRequired,
  or ActivityMoreInfo

TC-003 – Alternative Path: Boolean inversion for NoFilm and NoGuide

Given a prepaid excursion item where the upstream excursions API returns
  known values for isFilmingAllowed and isGuideAvailable
When the customer calls GET INT142 for that booking
Then ActivityMoreInfo.NoFilm and ActivityMoreInfo.NoGuide reflect
  the agreed inversion logic as confirmed by the SA
And the expected boolean values for NoFilm and NoGuide are [TO BE CONFIRMED]
  pending SA confirmation of inversion semantics

TC-004 – Error Scenario: Unauthenticated request

Given a request is made to INT142 without a valid authentication token
  (no Authorization header, expired token, or invalid token)
When the request is received by INT142
Then an HTTP 401 Unauthorised is returned
And no booking data is returned
And authentication enforcement is not affected by the field mapping changes
  introduced in this CR
