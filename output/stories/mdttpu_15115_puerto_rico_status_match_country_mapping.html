CR: Fix Puerto Rico Country Mapping for Status Match (US Site)

Interface: INT010.3 | Initiative: MDTTPU — US Market Rollout | Status: Draft

Jira Ticket: MDTTPU-15115

Summary

When a customer with a Puerto Rico (PR) address submits a status match via the US website, INT010.3 currently populates the CH001 country field with the website country (US) rather than the customer's country of address (PR). For all markets previously rolled out, the website country and the customer's country of address were identical, so this bug was never triggered. The US market introduces Puerto Rico as a distinct address country on a US-market site, exposing the mapping gap. This CR fixes the source of the country field in INT010.3 and aligns the downstream mappings in CRM AS IS, CHUB, and Salesforce to accept and correctly handle the PR country code.

Change Scope

  • INT010.3 — CH001 country field source: Change the source of the country field sent to CH001 (Customer SAPI POST /customers) from website country to country of address. This ensures Puerto Rico customers are identified with country code PR rather than US.
  • CRM AS IS — paese mapping: Add PRI + eng as a valid language/country combination in the CRM AS IS paese mapping, so that Puerto Rico (ISO alpha-3: PRI) with English (eng) is accepted and correctly resolved.
  • CHUB — country of residence mapping: Add PR to the country of residence mapping table so that PR is correctly translated to the corresponding CHUB country of residence country code.
  • Salesforce S008 — Country__c mapping: Add PR to the S008 Country__c mapping so that Puerto Rico is correctly populated in the Salesforce country field.

Interfaces Affected

  • INT010.3 — POST status-matches (MuleSoft → CHUB / CRM AS IS / Salesforce)
    The CH001 country field currently takes the value from the website's market/locale (US) rather than from the customer's country of address. The fix changes this to use country of address, so that Puerto Rico customers receive PR as their country value throughout the downstream systems.
    Confluence: INT010.3 — POST status-matches (Customer SAPI section)

Rationale

  • Puerto Rico is a US territory whose residents have a PR country of address, but who access the MSC website via the US market site. The current mapping logic assumes that the website country and the customer's country of address are always the same — an assumption that was valid for all previously rolled-out markets (IE, UK, DACH, MED) but breaks for Puerto Rico on the US site.
  • Without this fix, Puerto Rican customers submitting a status match will have their country recorded as US in CHUB, CRM AS IS, and Salesforce, resulting in incorrect customer data and potential downstream issues (e.g. incorrect language/country combination rejected by CRM AS IS, wrong country of residence stored in CHUB, incorrect Salesforce country field).
  • Requested by the MSC team as part of the US market rollout (September 2026). Raised in MDTTPU-15115.

Acceptance Criteria

GIVEN a customer whose country of address is Puerto Rico (PR) submits a status match via the US market website
WHEN INT010.3 calls Customer SAPI POST /customers (CH001)
THEN the country field is populated with PR (country of address), not US (website market country)

GIVEN a PR country code is passed to the CRM AS IS paese mapping
WHEN the mapping logic resolves the paese value
THEN PRI + eng is accepted as a valid combination and the correct paese value is returned without error

GIVEN a PR country code is passed to the CHUB country of residence mapping
WHEN the mapping logic resolves the CHUB country of residence value
THEN PR is mapped to the correct CHUB country of residence country code and stored on the customer record

GIVEN a PR country code is passed to the Salesforce S008 Country__c mapping
WHEN the mapping logic resolves the Salesforce country value
THEN the Country__c field is populated with the correct PR value in Salesforce

GIVEN a customer from any previously released market (IE, UK, DACH, MED) submits a status match
WHEN INT010.3 processes the request
THEN existing behaviour is unchanged — no regression introduced for markets where website country and country of address are the same
