BA Stories – Booking Group Management

Splitting Rationale

Two Change Requests are raised for this feature. Each CR maps to a distinct integration stream, a separate Jira ticket, a different source system, and a different downstream target. CR-1 covers a synchronous webform-to-Salesforce interface (INT101), while CR-2 covers an asynchronous event pipeline from DTS Booking Events to CDP spanning three closely related interfaces (INT024.1, INT100, INT025). The three interfaces in CR-2 are consolidated into a single CR because they carry the same change — adding the GroupType field to the BookingContext forwarded to CDP — and share a common DTS source event, a common downstream target, and a single Jira ticket (MDTTPU-6140). Separating them would produce three near-identical CRs with no additional clarity.

StoryScopeReason for separation (or consolidation)
CR-1: INT101 – Add Group ID to Webform Case Creation INT101 – MSC Book webform to Salesforce Case creation. Accepts and forwards the new optional groupId field. Separate CR: different source system (MSC Book), different target (Salesforce), separate Jira ticket (MDTTPU-8133), synchronous request/response pattern.
CR-2: Booking Events – Add GroupType to BookingContext (INT024.1, INT100, INT025) INT024.1, INT100, INT025 – DTS Booking Events to CDP. Accepts and forwards the new GroupType field within BookingContext. Consolidated into one CR: same change (forward GroupType from DTS to CDP), same source event, same downstream target, single Jira ticket (MDTTPU-6140). Three interfaces are affected but the change is additive and uniform across all three.

CR: INT101 – Add Group ID to Webform Case Creation

FieldValue
TypeCR
Jira TicketMDTTPU-8133
SummaryINT101 – Add Group ID to Webform Case Creation: accept and forward the new optional groupId field from MSC Book Help Center, Need Help, and Group Request webforms to Salesforce Case creation.
Change Scope Interface INT101 (MSC Book → MuleSoft → Salesforce). MuleSoft changes:
  • Accept the new optional field groupId (string, max 255 characters, character format [TO BE CONFIRMED]) in the inbound INT101 request payload from MSC Book.
  • Validate the field: if present, reject requests where groupId exceeds 255 characters or fails character-format validation [TO BE CONFIRMED] with an appropriate error response to MSC Book.
  • Map and forward groupId to Salesforce field groupId__c on the Case creation request. If absent from the inbound payload, the field is omitted (null) in the outbound Salesforce request.
  • Scope applies to DTP rolled-out markets only (Ireland, UK, DACH, MED+Latam, US). Non-DTP markets continue on the existing path unchanged.
  • Existing INT101 behaviour (case creation, agency/customer lookup, caseId response, Genesys routing trigger) is unchanged.
Rationale Travel Agency users submit Help Center, Need Help, and Group Request forms on MSC Book without the Group ID being automatically captured on the resulting Salesforce Case. Contact centre agents are forced to manually look up the Group ID from DTS, adding handling effort and introducing risk of error. This change closes that gap by passing the groupId entered on the form through INT101 to Salesforce, so agents have immediate visibility of the group booking identifier on the Case record.

GivenWhenThen
A valid INT101 webform request is received from MSC Book for a DTP rolled-out market, and the payload contains a groupId value within the permitted length and character format [TO BE CONFIRMED] MuleSoft INT101 processes the request MuleSoft forwards the request to Salesforce with groupId mapped to groupId__c, and returns HTTP 204 with no body to MSC Book
A valid INT101 webform request is received from MSC Book for a DTP rolled-out market, and the payload does not contain a groupId field MuleSoft INT101 processes the request MuleSoft forwards the request to Salesforce without the groupId__c field (field is absent or null), and returns HTTP 204 with no body to MSC Book. No error is raised due to the absence of the field.
A valid INT101 webform request is received from MSC Book for a DTP rolled-out market, and the groupId value in the payload exceeds 255 characters MuleSoft INT101 attempts to process the request MuleSoft rejects the request before forwarding to Salesforce and returns an error response to MSC Book identifying groupId as invalid due to exceeding the maximum permitted length. A valid INT101 webform request is received from MSC Book for a DTP rolled-out market and contains a valid groupId, but the Salesforce endpoint is unavailable MuleSoft INT101 attempts to forward the request to Salesforce and exhausts all configured retries MuleSoft returns an error response to MSC Book indicating the downstream service is unavailable. No partial case is created.
An INT101 webform request is received from MSC Book for a non-DTP market MuleSoft INT101 processes the request MuleSoft routes the request via the existing non-DTP path, unchanged. The groupId field, if present, is ignored and not forwarded. Existing behaviour is preserved.

CR: Booking Events – Add GroupType to BookingContext (INT024.1, INT100, INT025)

FieldValue
TypeCR
Jira TicketMDTTPU-6140
SummaryBooking Events – Add GroupType to BookingContext: accept and forward the new GroupType field from DTS Booking Events to CDP across INT024.1, INT100, and INT025.
Change Scope Interfaces INT024.1 (Booking Event Subset Legacy Orchestration), INT100 (Booking Profile Orchestration), and INT025 (Booking Event Orchestration) — all receiving DTS Booking Events and publishing to CDP. MuleSoft changes across all three interfaces:
  • Accept the extended DTS Booking Event payload that includes the new optional GroupType field within the booking context, once DTS delivers the event extension [TO BE CONFIRMED — DTS delivery date].
  • Map and forward GroupType to the corresponding field in the CDP target schema for each interface: A007 (INT024.1), A086 (INT100), A087 (INT025). Target field paths [TO BE CONFIRMED].
  • For group bookings (booking type GRP): GroupType is present in the DTS event and must be included in the payload forwarded to CDP.
  • For individual bookings (booking type IND): GroupType is absent or null in the DTS event. MuleSoft must process the event normally without error and not include the field in the CDP payload (or forward it as null, per CDP schema requirements [TO BE CONFIRMED]).
  • Existing orchestration logic for each interface (event subset filtering, GoldenID enrichment in INT024.1, participant splitting and filtering, booking profile generation in INT100, item/participant filtering in INT025) is unchanged.
  • The change is additive and backward-compatible. Existing CDP consumers and other downstream consumers that do not process GroupType must not be affected.
Rationale Booking events published by DTS to downstream consumers do not currently carry information about whether a booking is a group or individual booking. Downstream systems such as CDP (Adobe Customer Data Platform) cannot distinguish between group and individual bookings for segmentation and marketing activation purposes. This change extends the booking event payload forwarded to CDP to include GroupType, allowing CDP and other authorised consumers to correctly identify and segment group bookings. The change is additive and does not affect existing consumers.

Acceptance Criteria

GivenWhenThen
A DTS BK_CREATION_EVENT (or other applicable booking event type) for a group booking (type GRP) is published to Kafka topic R024 with GroupType populated MuleSoft INT024.1 receives the event, applies the event subset filter, performs GoldenID enrichment where required, and splits the event per participant MuleSoft INT024.1 forwards the event to CDP (schema A007) with GroupType included and correctly mapped to the target field path [TO BE CONFIRMED]. At least one split participant record meeting the Minimum Minor Age criteria with a valid GoldenID is forwarded successfully.
A DTS booking event for an individual booking (type IND) is published to Kafka topic R024 without the GroupType field MuleSoft INT024.1 receives and processes the event through the standard orchestration flow MuleSoft INT024.1 forwards the event to CDP without GroupType in the payload. No error is raised due to the absence of the field. Existing orchestration behaviour is unchanged.
A DTS booking event for a group booking (type GRP) is published and INT100 receives the event subset with GroupType populated MuleSoft INT100 applies participant filtering and generates the booking profile per participant MuleSoft INT100 forwards the booking profile to CDP (schema A086) with GroupType included and correctly mapped to the target field path [TO BE CONFIRMED].
A DTS booking event for an individual booking (type IND) is received by INT100 without the GroupType field MuleSoft INT100 processes the event through the standard booking profile orchestration flow MuleSoft INT100 forwards the booking profile to CDP without GroupType. No error is raised. Existing orchestration behaviour is unchanged.
A DTS booking event for a group booking (type GRP) is published and INT025 receives the event subset with GroupType populated MuleSoft INT025 applies item and participant filtering MuleSoft INT025 forwards the event to CDP (schema A087) with GroupType included and correctly mapped to the target field path [TO BE CONFIRMED].
A DTS booking event for an individual booking (type IND) is received by INT025 without the GroupType field MuleSoft INT025 processes the event through the standard orchestration flow MuleSoft INT025 forwards the event to CDP without GroupType. No error is raised. Existing orchestration behaviour is unchanged.
A DTS booking event containing the new GroupType field is processed by INT024.1, INT100, or INT025 The event is forwarded to CDP and any other existing downstream consumers registered on the same topic Existing downstream consumers that do not process GroupType continue to receive and process the event without error. The change is backward-compatible and no existing consumer integration is broken.
