Feature Summary

The Hold Option feature (INT-006) enables MSC website customers to reserve a cabin hold on a cruise booking through the B2C booking funnel. When a hold option is created, a CDP (Customer Data Platform) event is fired to support downstream CRM and marketing workflows — in particular, customer-facing email templates managed via Cheetah. Currently, the Hold Option CDP event contains insufficient data for these templates to render useful, personalised content.

This feature enriches the Hold Option CDP event with four additional fields: ship code, cabin category code, itinerary description, and cruise length. The ship code (derived from the first two letters of the Cruise ID) and cabin category code are sourced directly from the booking funnel data already available within INT-006. The itinerary description and cruise length are sourced from the DTS Itinerary Details API, which is already called (non-blocking) at the start of the INT-006 flow. The full port list was considered but deferred to a future iteration due to poor suitability for email templates (world cruises can have up to 55 ports). Ship name in full localised form was identified as a gap — it is not returned by the POST booking response and would require a dependency on DTS to extend that response; this is noted as an open item.

The change is scoped to the MuleSoft INT-006 integration. MuleSoft is responsible for populating the additional fields in the CDP event payload. Business logic for mapping ship code to full ship name, and any localisation of field values for email templates, is handled downstream by the CDP/Cheetah layer and is out of scope for MuleSoft. Cabin category code is sent as-is (comma-separated if multi-cabin, though multi-cabin bookings are not yet live on the website UI).

Business Requirements

Format: As a [actor] I want to [action] so that [benefit]

ID Requirements Description
BR-001 As a CRM/Marketing team member I want the Hold Option CDP event to include the ship code so that downstream email templates can display ship-related information to the customer. The ship code is derived from the first two letters of the Cruise ID, which is already available in the INT-006 flow. Full ship name is not available from the POST booking response; mapping ship code to full name is the responsibility of the downstream CDP/Cheetah layer. A dependency on DTS to extend the POST booking response with ship name has been identified as an open item.
BR-002 As a CRM/Marketing team member I want the Hold Option CDP event to include the cabin category code so that downstream email templates can reference the customer's selected cabin category. The cabin category code (e.g. IR1, BB) is available from the B2C/website booking funnel. Full localised category description is not available from DTS and is therefore out of scope for MuleSoft. Multiple category codes are comma-separated (consistent with the abandoned cart integration). Multi-cabin bookings are not yet live on the website UI, so currently a single code is always sent.
BR-003 As a CRM/Marketing team member I want the Hold Option CDP event to include the itinerary description so that downstream email templates can display a concise summary of the cruise itinerary. The itinerary description is a short string returned by the DTS Itinerary Details API, which is already called non-blocking at the start of INT-006. If the itinerary API call fails, the hold option event must still be sent; the itinerary description field will be absent or null in that case. Full port list is excluded from scope for this iteration.
BR-004 As a CRM/Marketing team member I want the Hold Option CDP event to include the cruise length so that downstream Cheetah formula logic can conditionally display content based on the number of nights. Cruise length (number of nights) is available from the DTS Itinerary Details API response. As with the itinerary description, if the itinerary API call fails the field may be absent or null and the event must still be sent.
