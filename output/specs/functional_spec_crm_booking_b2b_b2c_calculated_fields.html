Feature Summary

This feature introduces two new calculated fields across three existing MuleSoft booking event integrations (INT-100, INT-025, INT-024.1) as part of the CRM Marketing Automation programme. The changes are driven by a requirement from the CRM and CDP teams to enable personalised post-booking marketing communications and audience segmentation based on booking channel and pricing context.

The new field is a B2B/B2C boolean indicator. The Data Transformation Service (DTS) will derive and transmit this boolean from the Booking Channel node within the booking event: a value of true represents a B2C booking, and a value of false represents a B2B booking. The MuleSoft integration layer will pass this field through to the CDP without applying further derivation logic; transformation from boolean to a business-friendly string representation (B2C / B2B) is handled on the CRM/CDP side. The agent type is intentionally excluded from this mapping as its cardinality is too complex to map directly to a binary classification. DTS is targeting delivery in its second pipeline iteration (end of August 2026), with production release windows planned for 07/Sep/2026 or 06/Oct/2026 / 10/Oct/2026.

Business Requirements

Format: As a [actor] I want to [action] so that [benefit]

ID Requirements Description
BR-001 As a CRM Marketing team I want to receive a B2B/B2C boolean indicator on each booking event so that I can segment customers by booking channel and deliver personalised post-booking communications. DTS derives the boolean from the Booking Channel node in the booking event. True = B2C; false = B2B. The MuleSoft layer passes this field through without transformation. CDP/CRM side converts to human-readable string (B2C / B2B) for campaign use.
BR-002 As a MuleSoft integration team I want the B2B/B2C boolean field propagated through INT-100, INT-025, and INT-024.1 so that all three booking event interfaces deliver a consistent and complete data payload to the CDP. The field must be added to all three interfaces. Interface agreement pages (owned by the Marketing team) must be updated to document the DTS source field, target CDP field, and any transformation logic for each interface.

Non-Functional Requirements

Requirement ID Interface Requirement Description Category Priority
NFR-001 INT-100, INT-025, INT-024.1 The addition of the B2B/B2C boolean field must not degrade the end-to-end processing latency of any of the three booking event interfaces. Existing SLA thresholds must continue to be met after the changes are deployed. Performance High
NFR-002 INT-100, INT-025, INT-024.1 If the B2B/B2C boolean field is absent or null in the incoming DTS message, the integration must not fail. The field should be passed as null or omitted from the outbound payload to the CDP, and the event must continue to be processed successfully. Availability High
NFR-003 INT-100, INT-025, INT-024.1 Any malformed or unexpected values in the new fields (e.g. a non-boolean value in the B2B/B2C field) must be handled gracefully. The integration must log an appropriate error and, where possible, continue processing the remainder of the event without data loss. Availability High
NFR-004 INT-100, INT-025, INT-024.1 The new fields must be included in existing audit and logging mechanisms. The values passed through for both fields must be observable in logs on the pts27 test environment (or equivalent) to support pre-production validation. Auditability Medium
NFR-005 INT-100, INT-025, INT-024.1 The changes must be backward compatible. Existing consumers of the booking event interfaces must not be affected by the addition of the new fields. The payload schema must be extended non-breakingly. Scalability High
NFR-006 INT-100, INT-025, INT-024.1 Security controls applied to the existing interfaces (authentication, authorisation, transport encryption) must be unchanged by this feature. No new security surface is introduced. Security High

The event is either forwarded with the field nulled out, or routed to a dead-letter / error queue as per the existing error handling policy.
