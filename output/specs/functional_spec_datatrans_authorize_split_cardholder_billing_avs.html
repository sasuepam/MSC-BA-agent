Feature Summary

The MSC US website is migrating from SiteCore to the DTTP (Digital Transformation & Technology Programme) platform. The current SiteCore implementation uses the DataTrans lightbox, which natively collects cardholder billing information (first name, last name, street, city, country, zip code) inline during the payment flow. This data is stored and visible in the DataTrans WebAdmin console, allowing the MSC US Finance team to perform manual fraud checks and Address Verification Service (AVS) checks. The DTTP architecture uses DataTrans Secure Fields, which does not natively capture billing address data, creating a gap between the current and target states.

The selected approach (ADR0059, Scenario A) is to extend the DataTrans authorize-split API to accept a new cardholder object containing billing details. When a US or Puerto Rico customer completes a card payment via the B2C booking funnel or My Area, the front end collects the cardholder billing fields and passes them to MuleSoft. MuleSoft acts as a pure passthrough, forwarding the cardholder object in the authorize-split call to DataTrans. DataTrans stores this data in the WebAdmin console, restoring the billing data visibility that existed in SiteCore. Automatic AVS enforcement is out of scope for day one; at go-live the MSC US Finance team will perform manual AVS checks using the stored data. AVS automatic activation is deferred to a separate future backlog item.

The solution is US- and Puerto Rico-specific at the front-end level. The Adobe/CMS configuration controls which markets surface the cardholder billing fields; MuleSoft applies no market-based logic and forwards whatever the front end provides. This design allows other markets (e.g. Italy, for a future 3DS cardholder enrichment requirement) to enable billing data collection without a new integration build. The US go-live target is 23/Sep/2026, with a dependency on DataTrans delivering the extended authorize-split API (sandbox and production) before end-to-end testing can be completed.

Payment method scope: This change applies to card payments only (Secure Fields). Apple Pay and Google Pay are explicitly out of scope: DataTrans confirmed that for wallet payments, AVS is not required because the wallet provider (Apple/Google) already tokenises the card and authenticates the payer through device biometrics or passcode and their own fraud controls. The risk that AVS is intended to address is therefore already managed by the wallet. B2C does not need to send cardholder billing fields for wallet-based transactions, and MuleSoft will not receive or forward cardholder data for those payment paths.

M4M (My MSC mobile) scope: M4M is in scope for this specification. For the M4M payment flow, cardholder billing data is collected on the M4M checkout screen and passed during transaction initialisation via INT187.

Business Requirements

Format: As a [actor] I want to [action] so that [benefit]

ID Requirements
BR-001 As the MSC US Finance team, I want cardholder billing details (first name, last name, street address, city, country, zip code) to be stored in the DataTrans WebAdmin console so that I can perform manual fraud prevention and AVS verification checks on US card transactions after migration to DTTP.
BR-002 As a US or Puerto Rico customer completing a card payment via the B2C booking funnel or My Area, I want to be able to enter my cardholder billing address so that my payment can be processed and my billing details are recorded for fraud-prevention purposes.
BR-003 As the MSC technology team, I want billing address collection to be configurable per market on the front end so that non-US markets are not impacted by this change and future markets can enable the same flow without a new integration build.
BR-004 As the MSC US Finance team, I want to be informed when a card payment transaction fails due to an AVS mismatch so that I can review the booking and follow up appropriately.
BR-006 As the MSC US technology team, I want wallet payments (Apple Pay, Google Pay) to be excluded from the cardholder billing data collection requirement so that the integration is not complicated by payment methods where AVS is already handled by the wallet provider.
BR-007 As a US or Puerto Rico customer completing a card payment via My MSC Mobile (M4M), I want to enter my cardholder billing address on the checkout screen so that my payment is processed and my billing details are recorded for fraud prevention purposes.

7. The payment authorization proceeds normally.
Note: The DataTrans init endpoint already natively supports a customer object; no API extension is required from DataTrans for this path. Email and phone are NOT included in the customer object (day-one scope, consistent with B2C). INT188 (settle) is not impacted by this change. US/Puerto Rico Customer AVS decline – booking created, payment failed (future state post AVS activation) 1. B2C Website calls INT007 (or INT140 / INT146) with cardholder object.
2. MuleSoft forwards cardholder object in authorize-split call to DataTrans.
3. DataTrans performs AVS check; acquirer returns AVS decline. DataTrans returns an error object: reason: "error", message: "declined by AVS check [acquirer-specific code]". Error codes vary by acquirer (e.g. Worldpay vs Worldline); MSC configuration can set match thresholds (e.g. partial address match accepted).
4. MuleSoft receives the AVS error response and surfaces it to B2C.
5. The booking is created but the payment fails. B2C thank-you page displays "booking created, transaction failed" message.
Note: Pre-authorization before booking creation is not viable for the US market due to data-logging constraints. Authorization occurs post-booking creation. NFR-001 INT007, INT140, INT146, INT187 The cardholder/customer object must be fully optional on the integration layer. INT007, INT140, INT146, and INT187 must continue to process requests that do not include a cardholder/customer object without error or change in behaviour. Existing non-US market integrations and the first (cart price load) INT187 call from M4M must not be impacted. Availability / Backward Compatibility High
NFR-004 INT007, INT140, INT146 The country field within the cardholder address object must be an ISO 3166-1 alpha-2 two-letter code. No transformation is required by MuleSoft as this standard is already in use across existing API country fields. The front end must present a dropdown (not free text) for country to enforce the ISO format. Data Quality High
