Feature Summary

When a customer books a cruise via the new MSC website and pays by PayPal, the OPT booking reference is not yet created at the time payment is captured. This means that the PayPal transaction is completed without a booking reference, leaving the Finance team unable to reconcile the PayPal payment to the booking without manual intervention.

The root cause is a behavioural difference between the old website (where the OPT booking was created before payment, so the booking reference was available in PayPal at payment time) and the new website (where the OPT booking is created after payment, so no booking reference is available at the point of PayPal capture).

ADR0023 evaluated several reconciliation options. The DataTrans (DTS) PATCH API — which would allow the booking reference to be written back to PayPal after OPT booking creation — was identified as the ideal long-term solution but is not achievable in the near term because DataTrans does not have this integration on its current roadmap.

The agreed short-term solution (ADR0023 Option B) is to pass the acquirerAuthorizationCode from the DataTrans authorisation step through to SAP via the existing DTS ApplyPayment API. The acquirerAuthorizationCode is a unique reference that is shared between DataTrans and PayPal at the time of authorisation, and SAP can use it as a reconciliation key to match PayPal transactions to bookings.

The implementation decision is to reuse the existing optional field DtsApplyPaymentRequestMessage.Payment.ReferenceNo in the ApplyPayment request, populating it with the acquirerAuthorizationCode value sourced from the DataTrans transaction. This approach was chosen over adding a new dedicated API field (Option A) because it requires no DTS API development and has no impact on existing API consumers.

A critical dependency: the DataTrans transaction status endpoint (called at the start of the integration) returns the acquirerAuthorizationCode only when the transaction is in "authorized" state (e.g. Klarna). For payment methods where the transaction is in "authenticated" state at that point — including PayPal (PAP), Card, Apple Pay, and Google Pay — the acquirerAuthorizationCode is not present in the status response and must instead be sourced from the DataTrans authorisation response (authorize-split endpoint called later in the flow).

This change affects two existing interfaces: INT007 (payment in the booking funnel) and INT146 (payment in the MyMSC private area). Both interfaces use the DTS ApplyPayment API. The same reconciliation problem has been confirmed to exist for INT140 and INT188, which use the DTS confItem flow; the requirements for those interfaces are not yet detailed in this specification due to open points still to be resolved.
