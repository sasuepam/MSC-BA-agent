Feature Summary

Background and Business Context

MSC Cruises offers All-Inclusive (ALLINC) onboard service packages that are sold in linked adult–minor pairs. Currently, the MuleSoft integration layer sources the relationships between adult and minor ALLINC items from the Content Management System (CMS). This dependency on CMS introduces a risk of data inconsistency.

DTS will return a linked-item-code field on ALLINC items within the /obs/prices endpoint, providing a direct and authoritative source for adult–minor item relationships. The strategic decision has been made to migrate all adult–minor ALLINC association logic across the affected MuleSoft integrations from CMS to DTS-sourced data.

Once deployed, all relationship validation will use DTS data exclusively. The CMS call within INT130 is retained solely for non-relationship content enrichment.

Business Requirements

IDREQUIREMENT
BR-001 As a B2C consumer I want to retrieve a list of available onboard services where ALLINC adult and minor packages are explicitly linked to each other so that I can present correct paired package options to guests.
BR-002 As a B2C consumer I want the existing CMS-sourced ALLINC relationship fields to remain available alongside the new DTS-sourced fields at first deployment of the change so that I can migrate my implementation without a breaking change.
BR-003 As a B2C consumer I want the system to validate that any ALLINC minor item included in a price-to-book request is a permitted associate of the ALLINC adult item in that request so that invalid package combinations are rejected before a booking is attempted.
BR-004 As a B2C consumer I want the system to validate that any ALLINC minor item included in a booking request is a permitted associate of the ALLINC adult item in that request so that only valid package combinations can be booked.
BR-005 As a B2C consumer I want the system to validate that any ALLINC minor item included in a refund request is linked to an ALLINC adult item present in the same refund request so that partial or orphaned refund requests for linked packages are rejected.
BR-006 As a B2C consumer I want the system to verify that all passengers holding an ALLINC minor item are included in the refund request so that partial refunds for all-inclusive minor packages are not permitted.
BR-007 As a B2C consumer I want to retrieve booking details that include adult–minor ALLINC relationship data for purchased items so that I can display the correct linked package information to guests post-booking.

Use Cases

UC# PreCondition Actor/s Use Case Functionality Expected Open Questions
UC-001 Consumer has a valid session. DTS /obs/prices endpoint returns ALLINC items. B2C consumer (MyMSC front end or third-party client) Retrieve available onboard services with DTS-sourced adult–minor ALLINC relationships (INT130)
  • Consumer calls INT130 – Get Onboard Services (Available Items).
  • INT130 determines which ALLINC items have an adult–minor relationship, based on DTS data. ALLINC items with no relationship are treated as standalone and apply to all applicable passengers without restriction.
  • Each adult ALLINC item that has a relationship is enriched with the list of its permitted related minor items.
  • Each minor ALLINC item that has a relationship is enriched with the list of adult items it is linked to, via reverse lookup across all adult items in the DTS response.
  • CMS is still called for non-relationship content enrichment data only.
  • The response returns both the new DTS-sourced relationship fields and the deprecated CMS-sourced relationship fields, to allow consumers to migrate without a breaking change.
 —
UC-002 Consumer has retrieved available items via INT130. Consumer submits a price-to-book request containing at least one ALLINC item. B2C consumer (MyMSC front end or third-party client) Validate ALLINC adult–minor combination at price-to-book (INT139)
  • Consumer calls INT139 – PriceToBook Items with ALLINC items in the request.
  • INT139 determines which ALLINC items in the request have an adult–minor relationship, based on DTS data.
  • For each adult ALLINC item in the request, INT139 derives the permitted related minor items.
  • INT139 verifies that the adult item is present for all applicable adult/senior passengers, and that the corresponding minor item is present for all applicable minor passengers — only where applicable minor passengers exist on the booking.
  • If DTS does not return a related minor item for an adult ALLINC item (because no applicable minor passengers are on the booking), the adult item is treated as standalone with no relationship constraint.
  • INT139 verifies that no ALLINC minor item in the request falls outside the permitted minor items derived from the adult items.
  • If validation fails, INT139 rejects the request with a specific error. If validation passes, INT139 proceeds with the price-to-book flow.
 —
UC-003 Consumer has completed price-to-book via INT139. Consumer submits a booking request containing at least one ALLINC item. B2C consumer (MyMSC front end or third-party client) Validate ALLINC adult–minor combination at booking time (INT140)
  • Consumer calls INT140 – Book Items with ALLINC items in the request.
  • INT140 applies the same adult–minor combination validation as INT139 (UC-002) at booking time.
  • If validation fails, the booking is rejected with a specific error. If validation passes, INT140 proceeds with the booking flow.
 —
UC-004 Consumer has a booking with at least one ALLINC item purchased. Consumer submits a refund request containing at least one ALLINC item. B2C consumer (MyMSC front end or third-party client) Validate ALLINC adult–minor combination at refund time (INT137)
  • Consumer calls INT137 – Refund Item with ALLINC items in the refund request.
  • INT137 determines which purchased ALLINC items have an adult–minor relationship, based on booking data.
  • For each adult ALLINC item in the refund request, INT137 derives the expected related minor item.
  • INT137 verifies that the refund request does not span more than one related adult–minor pair.
  • INT137 verifies that any ALLINC minor item in the refund request is the expected related minor of an adult item also in the request.
  • If a related minor item is expected and applicable passengers hold it, INT137 verifies it is included in the refund request.
  • If validation fails, INT137 rejects the request with a specific error. If validation passes, INT137 proceeds with the refund flow.
 —
UC-005 Consumer has an existing booking with purchased ALLINC items. DTS getBookings (R113) returns relationship data for purchased items (dependent on DTS tickets RES2-29207 and RES2-29208). B2C consumer (MyMSC front end or third-party client) Retrieve booking details with adult–minor ALLINC relationship data (INT142)
  • Consumer calls INT142 – Booking Details.
  • INT142 retrieves the purchased items from DTS and classifies each ALLINC item as adult or minor.
  • Each adult ALLINC item is enriched with the list of its related minor items (relatedMinorItems).
  • Each minor ALLINC item is enriched with the list of its related adult items (relatedAdultItems).
  • This relationship data is not currently returned to the consumer — this change adds it for the first time.
 Open: dependent on DTS tickets RES2-29207 and RES2-29208. Chiara/Filippo to retest the applicability field and raise a bug if still missing.
UC-006 Consumer submits a price-to-book or booking request containing an ALLINC item with price basis "P" (per passenger). B2C consumer (MyMSC front end or third-party client) ALLINC passenger-count authorisation at price-to-book / book (INT139 / INT140)
  • Consumer calls INT139 – PriceToBook Items or INT140 – Book Items with an ALLINC item priced per passenger.
  • The integration determines which passengers on the booking are eligible for the item, based on age and applicability rules defined by DTS.
  • Passengers who do not meet any eligibility criteria are skipped.
  • The request must include all eligible passengers — partial passenger requests are not permitted.
  • If no applicable passengers exist for the item, the request is considered valid without requiring the item.
  • If any eligible passenger is absent from the request, the request is rejected.
 —
UC-007 An ALLINC item has been purchased for one or more passengers in a booking. Consumer submits a refund request for an ALLINC item. B2C consumer (MyMSC front end or third-party client) ALLINC refund remaining passengers validation (INT137)
  • Consumer calls INT137 – Refund Item for an ALLINC item.
  • INT137 identifies all passengers in the booking who hold the same ALLINC item (across all prebookings).
  • All passengers holding the item must be included in the refund request — partial passenger refunds for ALLINC items are not permitted.
  • If any passenger holding the item is absent from the request, the refund is rejected.
  • If all relevant passengers are present, the refund flow proceeds.
