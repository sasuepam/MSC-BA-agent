Feature Summary

INT025 is a MuleSoft interface that ingests booking passenger change events emitted by DTS (the cruise booking and management system) and forwards relevant events to AJO (Adobe Journey Optimizer). AJO uses these events to trigger a reset of the contact plan (marketing journey) for the passenger whose details have changed.

The current implementation of INT025 propagates the BK_PAX_CHANGE_EVENT to AJO for all passengers within a booking when any passenger change is detected. The business requirement, raised in open point CRM2-10010, is to restrict propagation so that the event is only forwarded for the specific passenger(s) flagged with isChanged=true in the DTS event payload.

Within a single booking there may be multiple passengers distributed across multiple cruise segments (itineraries). A given passenger may appear on one or more cruise segments. When DTS flags a passenger as changed, INT025 must identify every cruise segment that contains that passenger and send the BK_PAX_CHANGE_EVENT to AJO for each booking-cruise-passenger combination (e.g. B1_C1_P1, B1_C2_P1). Cruise segments that do not include the changed passenger must not receive the event.

This change ensures that only the contact plan for the affected passenger is reset in AJO, preventing unnecessary resets for other passengers on the same booking. It applies to all change types covered by the parent requirement CRM2-9923: first name, last name, date of birth, email, mobile, language, biometric check-in completion, and credit card registration.

The business notes that real-time propagation is preferred; however, a maximum 12-hour delay is acceptable provided all updates are delivered by 10:00 AM.

Business Requirements

Format: As a [actor] I want to [action] so that [benefit]

ID Requirements Description
BR-001 As a Marketing Operations manager, I want AJO to receive a BK_PAX_CHANGE_EVENT only for the passenger whose details have actually changed so that only the contact plan for the affected passenger is reset and other passengers on the same booking are unaffected. When DTS emits a BK_PAX_CHANGE_EVENT, INT025 must inspect the isChanged flag on each participant in the payload. Only passengers where isChanged=true must have events forwarded to AJO. All other passengers on the same booking must be excluded from the event propagation for this invocation.
BR-002 As a Marketing Operations manager, I want AJO to receive a separate BK_PAX_CHANGE_EVENT for each cruise segment that the changed passenger appears on so that the contact plan reset is applied consistently across all itineraries the passenger is booked on. A changed passenger may appear on multiple cruise segments within a booking (e.g. B1_C1_P1 and B1_C2_P1). INT025 must send one event to AJO per booking-cruise-passenger combination for each cruise segment containing the changed passenger. Cruise segments that do not include the changed passenger must not be included.
BR-003 As a Marketing Operations manager, I want the change person event to be distinguishable from other event types in AJO so that the correct contact plan reset logic is triggered rather than a generic update flow. The DTS rule for identifying a "change person" event must be applied by INT025 when classifying the BK_PAX_CHANGE_EVENT. The classification rule is owned by DTS; INT025 must correctly interpret and preserve it when forwarding to AJO. Refer to CRM2-9923 for the authoritative definition of the change person rule.
BR-004 As a Marketing Operations manager, I want passenger profile changes — including first name, last name, date of birth, email, mobile, language, biometric check-in completion, and credit card registration — to be propagated to AJO in near real time so that AJO contact plans reflect the latest passenger data. All field-level changes listed in CRM2-9923 must be propagated by INT025. The preferred delivery window is real time; a maximum delay of 12 hours is acceptable provided all updates are delivered by 10:00 AM. Note: the business does not require AJO to be informed of which specific field changed — the event itself (with the correct passenger scope) is sufficient.

Its processing overhead must not cause the overall INT025 event ingestion latency to exceed the existing agreed SLA. NFR-002 INT025 If the forwarding of a BK_PAX_CHANGE_EVENT to AJO fails for one booking-cruise-passenger combination (e.g. AJO returns a 5xx error), INT025 must handle the failure without silently dropping other combinations in the same event. The error handling and retry strategy for partial failures across multiple booking-cruise-passenger combinations must be defined. Failed forwarding attempts must be logged with sufficient context (booking ID, cruise segment ID, passenger ID) to enable investigation and reprocessing. Error Handling High
NFR-003 INT025 INT025 must apply the filtering and routing logic idempotently. If DTS retransmits the same BK_PAX_CHANGE_EVENT (e.g. due to a timeout or retry on DTS side), INT025 must not produce duplicate events in AJO for the same booking-cruise-passenger combination. The idempotency mechanism (e.g. deduplication key, event ID check) must be confirmed with the development team. Reliability High
NFR-004 INT025 The business requires propagation to AJO in near real time. Where real-time delivery is not achievable, all BK_PAX_CHANGE_EVENTs must be delivered to AJO within 12 hours and before 10:00 AM on the day of processing. If INT025 relies on a queue or batch mechanism that could delay delivery beyond the 12-hour window, a monitoring alert must be configured to notify the operations team before the 10:00 AM deadline is breached. Availability / SLA High
