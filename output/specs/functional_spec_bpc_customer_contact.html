Feature Summary

The CRM team has identified a defect whereby the phone number entered by a customer during the B2C booking funnel is not correctly mapped to the mobile contact fields in DTS (the MSC reservation system). Specifically, the phone number is being sent in the PAXTelephoneNo field and the country code in PAXPrefTelephoneNo, when they should instead be sent in PAXCellular and PAXPrefCellular respectively. This mismatch causes DTS to receive incomplete or incorrectly categorised contact data, which in turn prevents guest services and communications teams from reliably contacting guests regarding important booking updates.

This feature corrects the field mapping for phone number and country code across all affected booking interfaces managed by the MuleSoft integration layer. The fix applies to the DTS Book Request payload (INT006, INT007, INT007.1, INT007.2) and to the DTS Datatrans payment initialisation call (INT004.4, INT139, INT145). Additionally, a mandatory validation rule is introduced to ensure that the first passenger must supply a phone number before a booking can be submitted. Downstream integrations to Customer Hub (CH001), Salesforce (S008), Genesys (GEN001), and Adobe CDP (A070) that consume the mobilePhone field from the website request are also identified as impacted and must source from the corrected field going forward.

The correction ensures that MSC's guest contact records in DTS accurately reflect the mobile phone number provided at the point of booking, supporting reliable post-booking communications across all active markets.

Business Requirements

Format: As a [actor] I want to [action] so that [benefit]

ID Requirements Description
BR-001 As a system integrator, I want the phone number entered during booking to be correctly mapped to the mobile fields in DTS so that guest contact information is accurate and usable for communications. The phone number field collected from the website booking funnel (passengerInformation.adults.details.mobilePhone) must be sent to DTS in PAXCellular (not PAXTelephoneNo). The corresponding country code (passengerInformation.adults.details.mobilePhonePrefix) must be sent to DTS in PAXPrefCellular (not PAXPrefTelephoneNo). This applies to both the BookRequest payload and the HoldOption payload.
BR-002 As a CRM team member, I want the phone number entered at booking to be mandatory for the first passenger so that a valid contact number is always available for post-booking guest communications. The booking funnel must enforce that the first passenger (PAX 1) provides a phone number before the booking can be submitted. This is a mandatory field validation. The requirement for subsequent passengers is not specified and is assumed optional unless confirmed otherwise.
BR-003 As a system integrator, I want the corrected mobile phone field to be consistently sourced across all downstream integrations so that all systems receiving passenger contact data are aligned. The following downstream systems consume the mobile phone number from the website booking request and must source from the corrected field: Customer Hub (CH001) via Last_Mobile_Number; Salesforce (S008) via Case.SuppliedPhone; Genesys (GEN001) via callbackNumbers (E.164 format); Adobe CDP (A070) via _msccruisessa.webform.contacts.mobilePhone. No other passenger data mappings are affected.
BR-004 As a system integrator, I want the corrected mobile phone source field to be applied to all Datatrans payment initialisation calls so that the customer phone number used for payment processing is accurate. Interfaces INT004.4, INT139, and INT145 all call DT006 (Init Transaction to Datatrans). The customer.phone field in those calls must be sourced from passengerInformation.adults.details.mobilePhone. The specific prior source field is not stated in the requirements; confirming the previous source is recommended to validate the change is correctly scoped.
BR-005 As a system integrator, I want all other fields and mappings to remain unchanged so that this fix does not introduce any unintended side effects on other booking or passenger data. Only the fields explicitly listed in the requirements are in scope. No impact on other passenger data mappings or booking flows has been identified. All other integrations and field mappings must remain as-is.
